# SSIO 部署运维

三种跑法按推荐度排序：**Docker**（最省事，升级只换镜像）→ **systemd**（裸机 Linux）→ **Windows 服务**（NSSM）。

> 本文里的 Docker 命令是按标准 Dockerfile/compose 写的；本仓库的构建环境没有 Docker，
> 镜像未在真机构建验证过。服务端入口、健康检查端点、迁移加载这些**可在本机验证的部分**
> 已实测通过（`node packages/server/dist/index.js` → `/v1/readyz` 返回 `{"ok":true,"db":true}`）。

---

## 0. 上线前必须做的事

```bash
# 两把钥匙必须自己生成，绝不能用默认值
openssl rand -hex 32   # → JWT_SECRET（≥32 字符）
openssl rand -hex 16   # → MASTER_KEY（≥16 字符）
```

服务端启动时会用 zod 校验环境变量，**缺这两项直接起不来**（故意的：宁可起不来，也不能带着默认密钥上线）。

其他变量：

| 变量 | 默认 | 说明 |
|---|---|---|
| `HOST` | `127.0.0.1` | 容器里必须设成 `0.0.0.0`，否则宿主访问不到 |
| `PORT` | `8100` | |
| `DATA_DIR` | `./data` | 数据库 + 存储对象都在这里，**这是唯一需要备份的目录** |
| `RATE_LIMIT_MAX` | `600` | 每 IP 每分钟请求上限 |
| `CORS_ORIGIN` | `*` | 浏览器直连时用；挂了反代且同源可以收紧 |
| `LOG_LEVEL` | `info` | |

## 1. Docker（推荐）

```bash
cp .env.example .env     # 填 JWT_SECRET / MASTER_KEY
docker compose up -d
docker compose logs -f ssio
```

- 数据落在命名卷 `ssio-data`（`docker volume inspect ssio-data` 看实际路径）；
- compose 里宿主端口绑的是 `127.0.0.1:8100`，对外请在前置 Nginx/Caddy 上做 TLS；
- 只改了代码要重新构建：`docker compose build && docker compose up -d`。

升级：

```bash
docker compose pull       # 或 docker compose build
docker compose up -d      # 卷不动，数据不丢
```

**注意**：降级（新版本 → 旧版本）可能因为迁移不兼容而失败。升级前先备份（见 §4）。

## 2. systemd（裸机 Linux）

```bash
sudo useradd -r -s /usr/sbin/nologin ssio
sudo mkdir -p /opt/ssio && sudo chown ssio:ssio /opt/ssio
```

把下面这些放到 `/opt/ssio`（保持相对结构，启动命令依赖它）：

```
package.json  pnpm-lock.yaml  pnpm-workspace.yaml  .npmrc
packages/shared/{package.json,dist}
packages/server/{package.json,dist,drizzle}     # drizzle 是迁移文件，启动时要读
```

```bash
cd /opt/ssio
sudo -u ssio pnpm install --frozen-lockfile --prod --filter '@ssio/server...'
sudo -u ssio pnpm rebuild better-sqlite3        # 原生模块按本机环境重建
sudo cp deploy/ssio.service /etc/systemd/system/
sudo systemctl daemon-reload && sudo systemctl enable --now ssio
systemctl status ssio
```

## 3. Windows 服务（NSSM）

```powershell
# 一次装好 NSSM：winget install NSSM.NSSM
powershell -ExecutionPolicy Bypass -File deploy\install-windows.ps1 -InstallDir C:\ssio
```

脚本会：校验产物存在 → 生成 `.env`（随机两把钥匙）→ 注册服务 → 启动 → 打 `/v1/readyz` 自检。
卸载：`deploy\uninstall-windows.ps1`（**只摘服务，不动数据**）。

## 4. 备份与恢复

备份不需要停服务：数据库用 `VACUUM INTO` 由 SQLite 引擎产出一致性快照
（直接复制 `ssio.db` 会因为 WAL 未 checkpoint 而拿到不一致的副本）。

```bash
# 备份（产物是一个目录：ssio.db + storage/ + meta.json）
pnpm backup --out /var/backups/ssio

# 恢复到某个备份（默认拒绝覆盖现有数据，必须显式 --force）
pnpm restore --from /var/backups/ssio/ssio-backup-20261001-120000 --force
```

- 恢复前**先停服务**，避免正在写入的进程与恢复打架；
- 覆盖时现有数据改名为 `*.pre-restore-<时间戳>` 保留，不会直接删；
- 恢复过程会清掉残留的 `-wal/-shm`（只换主库不删 WAL，SQLite 会拿旧日志回放新库 → 直接损坏）。

自动备份（每天 3 点，保留 14 天）：

```cron
0 3 * * * cd /opt/ssio && pnpm backup --out /var/backups/ssio && find /var/backups/ssio -maxdepth 1 -name 'ssio-backup-*' -mtime +14 -exec rm -rf {} +
```

Windows 计划任务用同样两条命令即可（`pnpm backup` 走 `pnpm.cmd`）。

## 5. 反向代理

SSIO 自己不终止 TLS。Caddy 最省事：

```caddyfile
ssio.example.com {
  reverse_proxy 127.0.0.1:8100
  # 上传大包时别让代理掐断
  request_body {
    max_size 100MB
  }
}
```

Nginx 记得放宽 `client_max_body_size`（分片默认 4 MiB，但单分片上限是 16 MiB）。

## 6. 运维检查清单

| 项 | 怎么查 | 期望 |
|---|---|---|
| 存活 | `curl :8100/v1/healthz` | `{"ok":true,...}` |
| 就绪（含数据库） | `curl :8100/v1/readyz` | `{"ok":true,"db":true}` |
| 磁盘 | `du -sh $DATA_DIR` | 存储对象都在 `DATA_DIR/storage` |
| 配额 | `GET /v1/storage/quota`（带 APIKey） | `usedBytes` 接近 `quotaBytes` 就该调配额 |
| 备份可用性 | 定期拿备份做一次**恢复演练** | 能恢复才算有备份 |

已知会自己清理的东西：过期上传会话与过期/吊销的 refresh token 由内置 janitor 每小时清一次（`buildApp({ janitorIntervalMs })`）。
**不会**自动清的：软删的文件对象与已下架版本（保留是为了可回滚），磁盘紧张时手工处理。
