# SSIO 快速上手

从零到"客户端能拉到更新"大约 10 分钟。所有命令都在仓库根目录跑，都实测过。

---

## 1. 本机跑起来

```bash
pnpm install
cp .env.example .env        # 里面已经有一对可用的随机密钥（仅本机开发用）
pnpm build
pnpm dev                    # 或 node packages/server/dist/index.js

curl http://127.0.0.1:8100/v1/readyz     # {"ok":true,"db":true}
```

> 上线前必须换掉 `JWT_SECRET` / `MASTER_KEY`（`openssl rand -hex 32`），
> 缺这两项服务**拒绝启动** —— 宁可起不来，也不能带着默认密钥上线。

## 2. 建应用 + 签发 APIKey

Master Key 是管理面的总钥匙，只在建应用/发 Key 时用；业务调用一律走 APIKey。

```bash
export SSIO_URL=http://127.0.0.1:8100
export SSIO_MASTER_KEY=$(grep MASTER_KEY .env | cut -d= -f2)

pnpm cli -- app create myapp --name "我的应用"
pnpm cli -- key issue --app myapp --scopes 'release:read,release:write,storage:read,storage:write'
```

CLI 会把 APIKey 存进 `~/.ssio/config.json`（权限 0600），之后的业务命令自动带上它，
**不用再碰 Master Key**。

## 3. 发一个版本

```bash
# 一条命令完成：上传包体 → 创建版本 → 发布
pnpm cli -- release publish --app myapp --version 1.0.0 \
  --file ./dist/Setup.exe --platform win --arch x64 --notes "首个版本"
```

输出（真实示例）：

```
  上传分片 1/1
已发布 1.0.0（stable/win/x64） 2048 KB，耗时 482 ms
{
  "version": "1.0.0", "sizeBytes": 2097152,
  "sha256": "5647f05e…31eee", "published": true, …
}
```

包体走分片上传（默认 4 MiB/片），服务端流式合并并**自己算 sha256** ——
客户端声明的值只是用来核对，服务端算的才是准的。

## 4. 客户端拉更新

```bash
curl -H "X-API-Key: <上一步签发的 Key>" \
  "http://127.0.0.1:8100/v1/releases/latest?platform=win&arch=x64&channel=stable&current=0.9.0&clientId=abc123"
```

```json
{
  "hasUpdate": true,
  "version": "1.0.0",
  "notes": "首个版本",
  "size": 2097152,
  "sha256": "5647f05e…31eee",
  "url": "http://…/v1/storage/raw/<appId>/26/10/01/<sha256>?exp=…&sig=…",
  "mandatory": false
}
```

三个容易踩的点：

- **`platform` 枚举是 `win|linux|android|any`，不是 `win32`**；
- 不传 `arch` 时服务端按 `any` 匹配，客户端应当传自己的架构；
- `url` 是**签名 URL**（默认 300 秒，最长 3600），拿到就尽快下载，别存起来慢慢用。

用 Node SDK 更省事（重试、续期、分页都内置）：

```ts
import { createClient } from '@ssio/node';

const client = await createClient({ baseUrl: 'http://127.0.0.1:8100', apiKey: KEY });
const latest = await client.releases.latest({ platform: 'win', arch: 'x64', current: '0.9.0' });
if (latest.hasUpdate) {
  await client.downloadToFile(latest.url, './update.exe', { sha256: latest.sha256 });
}
```

## 5. 发卡 + 核销

```bash
pnpm cli -- card batch --app myapp --total 100 --days 30 --payload '{"vip":true}'
pnpm cli -- card export <批次ID> --out cards.csv     # 明文 CSV，导出即销毁
```

- 明文**只在这一次导出时出现**，之后谁都拿不到（连数据库里都没有，只存 sha256）；
- 核销是幂等的：并发打过来只有一个"首次成功"，其余返回已核销；
- 想查单张卡状态：`GET /v1/cards/<掩码>/status`（掩码形如 `HFN8-****-7XB2`）。

## 6. 公告

```bash
pnpm cli -- announce post --app myapp --title "停机维护" --content-md "今晚 23:00-23:30" --level warning
```

客户端读 `GET /v1/announcements/active`：只返回**当前时间窗内生效**的，置顶优先。
未开始/已结束的不会出现在里面 —— 时间窗由服务端判定，客户端不用自己过滤。

## 7. 论坛与软件源（可选）

- 论坛 `POST /v1/forum/boards/{slug}/threads`：**发帖回复必须是用户 JWT**，
  APIKey 只能做管理动作（建板块/置顶/锁帖）。理由：APIKey 代表应用，
  拿它发帖会分不清"谁说的"。
- 软件源 `/v1/registry/*`：发布 `name + version + 元数据`，适合插件/资源包分发。
  和 `releases` 的区别 —— releases 认识平台、有灰度、能强制升级；registry 都不管。

## 8. 日常运维

```bash
pnpm backup --out /var/backups/ssio         # 不用停服务（VACUUM INTO 一致性快照）
pnpm restore --from <备份目录> --force      # 默认拒绝覆盖，必须显式 --force
systemctl status ssio                        # 或 docker compose ps
```

详见 [`04-部署运维.md`](04-部署运维.md)。

## 9. 常见错误对照

| 状态码 | 含义 | 先查什么 |
|---|---|---|
| 401 | 没带凭据 / 凭据无效 | 请求头是 `X-API-Key` 还是 `Authorization: Bearer`？用户 Token 与 APIKey 别混用 |
| 403 | 身份对但权限不够 | Key 的 scopes 里有没有这个操作需要的 scope |
| 404 | 资源不存在**或不属于当前应用** | 跨应用访问一律按 404 返回（不泄露存在性） |
| 409 | 冲突 | slug/版本号重复、卡密批次已导出过 |
| 413 | 请求体超限 | 分片超过 16 MiB，或改了 chunkSize 没同步 |
| 507 | 配额不足 | `GET /v1/storage/quota` 看 usedBytes；调 `quotaBytes` 或清理软删对象 |
